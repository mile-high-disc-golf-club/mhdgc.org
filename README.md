# mhdgc.org

The Mile High Disc Golf Club website, replacing the club's Google Site. It's a React Router app on Cloudflare Workers, with every page prerendered to static HTML. Work is tracked in [GitHub issues](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues), with [a milestone for each phase](https://github.com/mile-high-disc-golf-club/mhdgc.org/milestones).

## How a request is handled

```
request ──► Cloudflare edge
              │
              ├─ /api/*                         ──► Worker: API routes (worker/api.ts)
              ├─ a built file or prerendered page ──► static asset (build/client/…)
              └─ anything else                  ──► Worker: React Router renders the 404 page, status 404
```

All of this is configured in [`wrangler.jsonc`](wrangler.jsonc):

- **Pages are static files.** `prerender: true` in [`react-router.config.ts`](react-router.config.ts) renders every route without a parameter to HTML at build time. Static asset requests are free and unlimited, and don't run the Worker.
- **The Worker runs only for `/api/*` and for paths that match no file.** `run_worker_first: ["/api/*"]` sends API paths to it. Anything else that matches no file (`not_found_handling: "none"`) also reaches it, and React Router's catch-all route renders the 404 page with a real 404 status.
- **One URL per page.** `html_handling: "drop-trailing-slash"` serves `about/index.html` at `/about` and redirects `/about/` there.
- **Navigating between pages doesn't run the Worker either.** `routeDiscovery: { mode: "initial" }` puts the route manifest in the page, so the browser never fetches `/__manifest`. The exception is a link to a path that doesn't exist: the catch-all route has a `loader`, so the browser fetches its `.data` file, which the Worker answers with the 404.

## Layout

```
app/                       React Router app
  root.tsx                 Document, site shell and error boundary
  routes.ts                Route config; every path without a parameter is prerendered
  routes/                  One module per page, plus not-found.tsx (the catch-all)
  site.ts                  Site name, page titles and nav links
worker/
  index.ts                 Worker entry: /api/* first, then React Router
  api.ts                   API routes
shared/api.ts              Types shared by the app and the Worker
wrangler.jsonc             Cloudflare config: Worker, assets, vars
react-router.config.ts     SSR on, prerender everything, route discovery
vite.config.ts             Vite + @cloudflare/vite-plugin + React Router
worker-configuration.d.ts  Generated by `bun run cf-typegen` (commit it)
.dev.vars.example          Template for local vars and secrets (.dev.vars is gitignored)
```

TypeScript is split three ways (`tsconfig.app.json`, `tsconfig.worker.json`, `tsconfig.node.json`), so the Worker gets Workers runtime types instead of the DOM.

## Local development

**Bun installs, Node 24 runs.** Use Bun as the package manager and script runner, but don't use `--bun` or Bun-only APIs.

```bash
bun install
cp .dev.vars.example .dev.vars
bun run dev
```

Open http://localhost:5173. `vite dev` runs the Worker in **workerd**, the same runtime as production, so pages, the 404 and `/api/health` all work on one port.

| Script                 | What it does                                                                   |
| ---------------------- | ------------------------------------------------------------------------------ |
| `bun run dev`          | Dev server with HMR, running the Worker in workerd                             |
| `bun run build`        | Build the client and the Worker, then prerender every page into `build/client` |
| `bun run preview`      | Build, then serve the production output locally in workerd (port 4173)         |
| `bun run deploy`       | Build, then `wrangler deploy`                                                  |
| `bun run format`       | Format supported files with Prettier                                           |
| `bun run format:check` | Check Prettier formatting                                                      |
| `bun run lint`         | Generate types and run ESLint                                                  |
| `bun run test`         | Run Node and jsdom tests with Vitest                                           |
| `bun run storybook`    | Run component stories locally (port 6006)                                      |
| `bun run typecheck`    | Generate Worker and route types, then `tsc -b`                                 |
| `bun run cf-typegen`   | Regenerate `worker-configuration.d.ts` after changing `wrangler.jsonc`         |

To check what would be uploaded without deploying, run `bun run build && bunx wrangler deploy --dry-run`.

## Environment variables and secrets

| Kind                            | Where it lives                                                    | Committed?      |
| ------------------------------- | ----------------------------------------------------------------- | --------------- |
| Non-secret Worker config        | `vars` in `wrangler.jsonc`                                        | Yes             |
| Worker secrets (production)     | `bunx wrangler secret put NAME`, or the dashboard (type _Secret_) | No              |
| Worker vars and secrets (local) | `.dev.vars` (copy from `.dev.vars.example`)                       | No (gitignored) |

- The Worker reads them from the `env` argument to `fetch` (see `worker/api.ts`). After adding one, run `bun run cf-typegen` so `Env` gets the new key. Give a secret a placeholder in `.dev.vars.example` too.
- Locally, `.dev.vars` overrides `vars`. That's why `/api/health` shows `"env": "development"` locally and `"production"` once deployed. `wrangler deploy` never uploads `.dev.vars`.
- Prerendering runs at build time, so loaders on prerendered pages see the build's environment, not production's.
- `VITE_*` variables are compiled into the browser bundle, where anyone can read them. Never put secrets there.

## Deploying

GitHub Actions deploys pushes to `main` after CI passes, one production deploy at a time. GitHub can replace a pending deploy when another run enters the production concurrency group. Eligible pull requests from this repository upload a Worker version to the stable `pr-<number>` alias and update the PR comment with the preview URL. A PR gets no preview while it only changes files that never reach the site: the README, `CLAUDE.md`, agent config, GitHub config other than `ci.yml`, Storybook, stories, tests and lint or format config. The `Decide on a preview` step in [`ci.yml`](.github/workflows/ci.yml) lists them, and any other file triggers a preview. To run only the checks for one push, put `[skip deploy]` in the latest commit's message. Any case works, with the words in either order and joined by a space, hyphen or underscore, such as `[Skip-Deploy]` or `[deploy_skip]`. The PR comment keeps pointing at the last preview, and the next push without the tag brings it up to date. The tag doesn't apply to `main`, which deploys on every merge so production always matches it. GitHub's own `[skip ci]` skips the checks as well. Fork and Dependabot PRs run CI without uploading previews. A maintainer can review a fork contribution and open a PR from a branch in this repository to preview it. Preview runs trust contributors with write access because they build code from this repository's PR branches and use the deployment token.

Set up the [repository's Actions secrets](https://github.com/mile-high-disc-golf-club/mhdgc.org/settings/secrets/actions) before deploying:

- `CLOUDFLARE_API_TOKEN` uses **Workers Scripts → Edit** scoped to the club's Cloudflare account. To rotate it, create a replacement with the same scope, update the GitHub secret, verify a deployment, then revoke the old token. [Cloudflare API tokens](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/)
- `CLOUDFLARE_ACCOUNT_ID` holds the club's Cloudflare account ID. Update this secret and replace the token together if the Worker moves to a different account. [Find the Cloudflare account ID](https://developers.cloudflare.com/fundamentals/account/find-account-and-zone-ids/)

Before the first PR preview, set up the account's `workers.dev` subdomain in Cloudflare's Workers & Pages dashboard and deploy the Worker once with `preview_urls: true`. The first successful deploy from `main` creates the Worker. PR preview uploads fail until that deployment exists. [Deployment setup tracking issue](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/4)

Preview responses include `X-Robots-Tag: noindex`. The production `workers.dev` route stays off, and no domain points at the Worker yet, so a production deploy has no public URL until launch. It keeps the Worker's active version in step with `main`, and PR previews need it. Production uses `new.mhdgc.org` for board review ([#23](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/23)), then `www.mhdgc.org` at cutover ([#24](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/24)).

## Why it's built this way

### Hosting and rendering

- **Workers with static assets, not Pages.** Cloudflare's React Router guide uses Workers with the Cloudflare Vite plugin, and new platform features ship there first. It runs on the free plan.
- **React Router framework mode, prerendered.** The site is content that changes when someone edits it, not per visitor, so every page is rendered to HTML at build time. Crawlers and link previews get real content, and page views never run the Worker. The same routing, loaders and `meta` as dgtags carry over.
- **SSR stays on (`ssr: true`) rather than `ssr: false`.** With a static-only build, unknown paths would get the SPA fallback with a 200, or need a hand-built `404.html`. Keeping the server build lets the Worker render the 404 with a real status. It also leaves room for pages that can't be prerendered, such as event detail pages with their own link previews ([#27](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/27)), without changing the setup. The cost is a larger Worker upload (about 160 KB gzipped), which only runs for 404s and the API.

### Decisions recorded from planning

- **Content lives in the repo** as Markdown and data files, changed by pull request and read at build time ([#9](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/9)).
- **Events come from the club's Google Calendars.** The board keeps editing in Google Calendar, and `/api/events` reads the public ICS feeds and caches them ([#16](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/16), [#18](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/18)).
- **Design system copied from dgtags**, light theme only ([#5](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/5), [#6](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/6)).
- **The contact form stays a Google Form** for the MVP ([#13](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/13)), and moves to our own form later ([#25](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/25)).
- **Tooling matches dgtags:** Bun, ESLint, Prettier, Vitest, Storybook and lefthook ([#2](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/2)).
- **Launch is staged:** first on `new.mhdgc.org` for board review, then `www` moves over from the Google Site ([#23](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/23), [#24](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/24)).
