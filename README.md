# mhdgc.org

The Mile High Disc Golf Club website, replacing the club's Google Site. It's a React Router app on Cloudflare Workers, with every page prerendered to static HTML. Work is tracked in [GitHub issues](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues), with [a milestone for each phase](https://github.com/mile-high-disc-golf-club/mhdgc.org/milestones).

## How a request is handled

```
request ──► Cloudflare edge
              │
              ├─ /api/*                         ──► Worker: API routes (worker/api.ts)
              ├─ a built file or prerendered page ──► static asset (build/client/…)
              └─ anything else                  ──► Worker: React Router renders the 404 page, status 404

cron, every 15 minutes ──► Worker: refresh the events in KV from the Google Calendar API
```

All of this is configured in [`wrangler.jsonc`](wrangler.jsonc):

- **Pages are static files.** `prerender: true` in [`react-router.config.ts`](react-router.config.ts) renders every route without a parameter to HTML at build time. Static asset requests are free and unlimited, and don't run the Worker.
- **The Worker runs only for `/api/*` and for paths that match no file.** `run_worker_first: ["/api/*"]` sends API paths to it. Anything else that matches no file (`not_found_handling: "none"`) also reaches it, and React Router's catch-all route renders the 404 page with a real 404 status.
- **One URL per page.** `html_handling: "drop-trailing-slash"` serves `about/index.html` at `/about` and redirects `/about/` there.
- **Old home links redirect.** `public/_redirects` sends `/home` and `/home/` to `/` with status 301. `/membership`, `/about` and `/events` retain their Google Sites paths. Canonical URLs use `/` for home and no trailing slash for other pages. Facebook, Instagram, UDisc and Disc Golf Scene have not been audited for other old links.
- **Events load in the browser from `/api/events`, which reads Workers KV.** A cron trigger runs the Worker's `scheduled` handler every 15 minutes. For each calendar in [`content/calendars.json`](content/calendars.json), in parallel, it asks the Google Calendar API for every occurrence from the 1st of the current month (America/Denver) to 12 months ahead, and writes the result to the `EVENTS` namespace. Google expands repeating events, so the Worker only maps fields, in about a millisecond of CPU. If a calendar's request fails, that calendar keeps its last good events. `/api/events` returns the whole window from KV, with `Cache-Control: public, max-age=300, stale-while-revalidate=600`. If KV is empty, as on a first deploy, it runs the refresh inline once. The response type is `EventsResponse` in [`shared/api.ts`](shared/api.ts).
- **Navigating between pages doesn't run the Worker either.** `routeDiscovery: { mode: "initial" }` puts the route manifest in the page, so the browser never fetches `/__manifest`. The exception is a link to a path that doesn't exist: the catch-all route has a `loader`, so the browser fetches its `.data` file, which the Worker answers with the 404.

## Layout

```
app/                       React Router app
  root.tsx                 Document, icons, site shell (components/site-layout.tsx) and error boundary
  routes.ts                Route config; every path without a parameter is prerendered
  routes/                  One module per page, plus not-found.tsx (the catch-all)
  site.ts                  Site name, page titles, nav and social links
  brand/                   The club's badge and wordmark SVGs, imported with hashed URLs
public/                    Served as is at the root: favicon, touch icons, web manifest, Open Graph image
content/                   Page Markdown, board list, calendars and photos (see CONTENT.md)
worker/
  index.ts                 Worker entry: /api/* first, then React Router; the cron's scheduled handler
  api.ts                   API routes
  calendars.ts             content/calendars.json, as the content pipeline compiled it
  events/                  The events refresh: Calendar API client, descriptions, the window and KV
    fixtures/              Real Calendar API responses for the club's calendars, used by the tests
shared/api.ts              Types shared by the app and the Worker
shared/content-assets.ts   The image host and R2 bucket for content photos
scripts/                   upload-content-images.ts: encodes photos and uploads them to R2
wrangler.jsonc             Cloudflare config: Worker, assets, KV, cron trigger, vars
react-router.config.ts     SSR on, prerender everything, route discovery
vite.config.ts             Vite + @cloudflare/vite-plugin + React Router
worker-configuration.d.ts  Generated by `bun run cf-typegen` (commit it)
.dev.vars.example          Template for local vars and secrets (.dev.vars is gitignored)
```

TypeScript is split three ways (`tsconfig.app.json`, `tsconfig.worker.json`, `tsconfig.node.json`), so the Worker gets Workers runtime types instead of the DOM.

## Local development

**Bun installs, Node 24 runs.** Use Bun as the package manager and script runner, but don't use `--bun` or Bun-only APIs.

```bash
bun install
cp .dev.vars.example .dev.vars
bun run dev
```

Open http://localhost:5173. `vite dev` runs the Worker in **workerd**, the same runtime as production, so pages, the 404 and `/api/health` all work on one port.

**Events locally.** `bun run dev` and `bun run preview` use a local, simulated KV namespace in `.wrangler/state`, never the production one. Cron triggers don't run on their own locally. The first request to `/api/events` fills the empty KV from the Calendar API, which needs an internet connection and `GOOGLE_CALENDAR_API_KEY` in `.dev.vars` (ask a maintainer for the key, or create your own as described under Deploying). To run the scheduled handler, as the cron would, request its URL on either server:

```bash
curl "http://localhost:5173/cdn-cgi/handler/scheduled"
```

To empty the local KV and test the first-request refresh, run `bunx wrangler kv key delete "events:v1" --binding EVENTS --local`.

| Script                 | What it does                                                                   |
| ---------------------- | ------------------------------------------------------------------------------ |
| `bun run dev`          | Dev server with HMR, running the Worker in workerd                             |
| `bun run build`        | Build the client and the Worker, then prerender every page into `build/client` |
| `bun run preview`      | Build, then serve the production output locally in workerd (port 4173)         |
| `bun run deploy`       | Build, then `wrangler deploy`                                                  |
| `bun run format`       | Format supported files with Prettier                                           |
| `bun run format:check` | Check Prettier formatting                                                      |
| `bun run lint`         | Generate types and run ESLint                                                  |
| `bun run test`         | Run Node and jsdom tests with Vitest                                           |
| `bun run storybook`    | Run component stories locally (port 6006)                                      |
| `bun run typecheck`    | Generate Worker and route types, then `tsc -b`                                 |
| `bun run cf-typegen`   | Regenerate `worker-configuration.d.ts` after changing `wrangler.jsonc`         |

To check what would be uploaded without deploying, run `bun run build && bunx wrangler deploy --dry-run`.

The build copies [`public/_headers`](public/_headers) and adds security headers and a Content Security Policy for each prerendered page to `build/client/_headers`. It hashes the inline scripts from the generated HTML, so there are no hashes to update by hand. Local preview and deployed builds enforce the policy in [`shared/security-headers.ts`](shared/security-headers.ts), which is also where to allow new embed, asset or analytics origins, and any other site a form on our pages posts to (`form-action`). Chromium also applies `form-action` to redirects after a form post, so a handler that redirects a submission to another site needs that site allowed too. The Worker applies security headers to its own responses and authorizes the 404 page's inline scripts with a per-response nonce.

## Environment variables and secrets

| Kind                            | Where it lives                                                    | Committed?      |
| ------------------------------- | ----------------------------------------------------------------- | --------------- |
| Non-secret Worker config        | `vars` in `wrangler.jsonc`                                        | Yes             |
| Worker secrets (production)     | `bunx wrangler secret put NAME`, or the dashboard (type _Secret_) | No              |
| Worker vars and secrets (local) | `.dev.vars` (copy from `.dev.vars.example`)                       | No (gitignored) |

- The Worker reads them from the `env` argument to `fetch` (see `worker/api.ts`). After adding one, run `bun run cf-typegen` so `Env` gets the new key. Give a secret a placeholder in `.dev.vars.example` too.
- Locally, `.dev.vars` overrides `vars`. That's why `/api/health` shows `"env": "development"` locally and `"production"` once deployed. `wrangler deploy` never uploads `.dev.vars`.
- Prerendering runs at build time, so loaders on prerendered pages see the build's environment, not production's.
- `VITE_*` variables are compiled into the browser bundle, where anyone can read them. Never put secrets there.

## Deploying

GitHub Actions deploys pushes to `main` after CI passes, one production deploy at a time. It deploys the build that the CI checks job made and tested, saved as a `build` artifact for a week, rather than building again. GitHub can replace a pending deploy when another run enters the production concurrency group. Eligible pull requests from this repository upload a Worker version to the stable `pr-<number>` alias and update the PR comment with the preview URL. A PR gets no preview while it only changes files that never reach the site: the README, `CLAUDE.md`, agent config, GitHub config other than `ci.yml`, Storybook, stories, tests and lint or format config. The `Decide on a preview` step in [`ci.yml`](.github/workflows/ci.yml) lists them, and any other file triggers a preview. To run only the checks for one push, put `[skip deploy]` in the latest commit's message. Any case works, with the words in either order and joined by a space, hyphen or underscore, such as `[Skip-Deploy]` or `[deploy_skip]`. The PR comment keeps pointing at the last preview, and the next push without the tag brings it up to date. The tag doesn't apply to `main`, which deploys on every merge so production always matches it. GitHub's own `[skip ci]` skips the checks as well. Fork and Dependabot PRs run CI without uploading previews. A maintainer can review a fork contribution and open a PR from a branch in this repository to preview it. Preview runs trust contributors with write access because they build code from this repository's PR branches and use the deployment token.

Set up the [repository's Actions secrets](https://github.com/mile-high-disc-golf-club/mhdgc.org/settings/secrets/actions) before deploying:

- `CLOUDFLARE_API_TOKEN` uses **Workers Scripts → Edit** scoped to the club's Cloudflare account. To rotate it, create a replacement with the same scope, update the GitHub secret, verify a deployment, then revoke the old token. [Cloudflare API tokens](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/)
- `CLOUDFLARE_ACCOUNT_ID` holds the club's Cloudflare account ID. Update this secret and replace the token together if the Worker moves to a different account. [Find the Cloudflare account ID](https://developers.cloudflare.com/fundamentals/account/find-account-and-zone-ids/)
- `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` are an R2 API token with **Object Read & Write** on the `mhdgc-content-images` bucket only, for the image upload job. See [Content images in R2](#content-images-in-r2).

Events need two one-time setups, both already done for the club:

- **The `EVENTS` KV namespace**, in the club's Cloudflare account ("Tech@mhdgc.org's Account"). Its ID is in `wrangler.jsonc`. Check `bunx wrangler whoami` shows the club's account first, because a personal Cloudflare login has its own account, and a namespace created there can't be bound. To create it again, run `bunx wrangler kv namespace create EVENTS`, decline the offer to edit `wrangler.jsonc` (it reformats the file), put the new ID in `kv_namespaces`, and run `bun run cf-typegen`.
- **A Google Calendar API key**, as the Worker secret `GOOGLE_CALENDAR_API_KEY`. It lives in the `prod-website` project in the club's Google Cloud organization (mhdgc.org, signed in with a club Workspace account). To replace it, in the [Google Cloud console](https://console.cloud.google.com): enable the **Google Calendar API**, then **APIs & Services → Credentials → Create credentials → API key**, with **Application restrictions: None** (the Worker sends no referrer and has no fixed IP) and **API restrictions** set to the Google Calendar API only. Then run `bunx wrangler secret put GOOGLE_CALENDAR_API_KEY` and delete the old key. The API is free, with a quota of 1,000,000 requests a day, against about 600 from the cron. The key only reads public calendars, and it stays in the Worker, never in the browser bundle.
  Deploying registers the cron trigger, and its runs show in the Worker's Observability logs. Cron triggers only run on the deployed version, and PR previews read the same namespace, so a preview shows production's latest refresh. A calendar that a PR adds to `calendars.json` is missing from its preview, which returns `partial: true`, until the PR is merged and deployed.

Before the first PR preview, set up the account's `workers.dev` subdomain in Cloudflare's Workers & Pages dashboard and deploy the Worker once with `preview_urls: true`. The first successful deploy from `main` creates the Worker. PR preview uploads fail until that deployment exists. [Deployment setup tracking issue](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/4)

Previews and the review host stay out of search results. The CI preview step adds `X-Robots-Tag: noindex` for every static file to `build/client/_headers`. On `beta.mhdgc.org`, a host rule in [`public/_headers`](public/_headers) does the same for production's static files. The Worker runs first for `/robots.txt` and, on `beta.mhdgc.org` and `*.workers.dev`, serves one that disallows crawling and adds the noindex header to its own responses ([`worker/robots.ts`](worker/robots.ts)). Every other host gets production's static `public/robots.txt`, which allows crawling and points to `sitemap.xml`. `buildEnd` in `react-router.config.ts` writes the sitemap from the prerendered pages, so it leaves out the 404 page and the `/home` redirect. The production `workers.dev` route stays off, so production is reached only through its custom domains. Every merge to `main` still deploys, which keeps the Worker's active version in step with `main`, and PR previews need that.

### Custom domains

Production is served on `beta.mhdgc.org` for board review ([#23](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/23)), then on `www.mhdgc.org` at cutover ([#24](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/24)). Each is a Workers **Custom Domain**, added once in the Cloudflare dashboard rather than in `wrangler.jsonc`: **Workers & Pages → mhdgc-org → Settings → Domains & Routes → Add → Custom domain**. Cloudflare creates the DNS record and certificate, so don't add a CNAME by hand. Keeping domains out of `wrangler.jsonc` means the deploy token needs no permissions on the `mhdgc.org` zone, which also holds the club's email records. `wrangler deploy` only changes custom domains when `wrangler.jsonc` lists some, so deploys leave the dashboard's alone. To take the review host down, remove the custom domain there.

### Analytics

Page views go to [Cloudflare Web Analytics](https://developers.cloudflare.com/web-analytics/), which sets no cookies, so the site needs no consent banner. See the stats in the club's Cloudflare dashboard under **Web Analytics**, on the `www.mhdgc.org` site.

The beacon is added by the site's own code rather than Cloudflare's automatic injection. Every host serves the same prerendered HTML, so after hydration [`app/root.tsx`](app/root.tsx) loads the beacon only when the page is on `www.mhdgc.org` ([`app/lib/web-analytics.ts`](app/lib/web-analytics.ts)). PR previews, `beta.mhdgc.org` and local servers aren't counted. The beacon counts client-side route changes itself, so React Router navigations show up as page views. The Content Security Policy in [`shared/security-headers.ts`](shared/security-headers.ts) allows its script from `static.cloudflareinsights.com` and its reports to `cloudflareinsights.com`.

To set it up, add `www.mhdgc.org` as a site in **Web Analytics**. If the dashboard sets it up automatically, choose **Manage site** and change it to **Enable with JS Snippet installation**, since a page can only have one beacon. Copy the token from the site's JS snippet into `webAnalyticsToken` in [`app/site.ts`](app/site.ts). The token is public, since it's in every page. Setting it to `''` turns analytics off.

## Editing content

See [CONTENT.md](CONTENT.md) for editing pages and board data in GitHub, adding photos,
and checking PR previews. Markdown and schemas run at build time through
`content.config.ts`; routes read the compiled output through `~/.server`. Photos are
encoded once, outside the build, and served from R2 (below).

## Content images in R2

Encoding photos to AVIF and WebP at several widths took minutes on every dev start and
build ([#47](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/47)), so the
build no longer does it ([#49](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/49)).
`content.config.ts` reads each photo's size from its header and hashes its bytes, and
links to `https://assets.mhdgc.org/v1/<hash>/<width>.<format>`. The `Upload content
images` job in CI runs `bun run images:upload`, which lists each photo's folder in the
`mhdgc-content-images` R2 bucket and encodes and uploads only the files that are
missing. Deploys wait for it. Fork and Dependabot PRs can't read the secrets, so their
photos are uploaded when they merge to `main`. Objects are never overwritten or
deleted: a changed photo gets new keys, so they're cached as immutable and old
previews keep working. The script only adds files, but the token's Object Read &
Write permission can also overwrite and delete them, and same-repository PRs run the
PR's own copy of the script. So the guarantee relies on trusting people with push
access, as previews already do.

`bun run dev` serves the originals from `/content-assets/` instead, with no AVIF or
WebP versions, so it needs no network or encoding. `CONTENT_IMAGES=local bun run build`
does the same for a build without R2.

One-time setup in the club's Cloudflare account:

1. **R2 → Create bucket** named `mhdgc-content-images`, with automatic location.
2. In the bucket's **Settings → Custom Domains**, connect `assets.mhdgc.org`. This
   needs `mhdgc.org` as a zone in the same account. Leave the `r2.dev` URL off: it's
   rate-limited and not meant for production.
3. **R2 → Manage API tokens → Create API token** with **Object Read & Write**, applied
   to `mhdgc-content-images` only. Save its **Access Key ID** and **Secret Access Key**
   as the repository's Actions secrets `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`.
   The job also uses `CLOUDFLARE_ACCOUNT_ID`.
4. Re-run CI on `main`, or push any commit, so the job uploads the existing photos.

Until this is done, the upload job fails, so previews and production deploys don't run.
To upload from your machine, put the three variables in your shell and run
`bun run images:upload` (`--dry-run` lists what's missing). The host and bucket names are
in [`shared/content-assets.ts`](shared/content-assets.ts), and the Content Security
Policy allows images from that host.

## Why it's built this way

### Hosting and rendering

- **Workers with static assets, not Pages.** Cloudflare's React Router guide uses Workers with the Cloudflare Vite plugin, and new platform features ship there first. It runs on the free plan.
- **React Router framework mode, prerendered.** The site is content that changes when someone edits it, not per visitor, so every page is rendered to HTML at build time. Crawlers and link previews get real content, and page views never run the Worker. The same routing, loaders and `meta` as dgtags carry over.
- **SSR stays on (`ssr: true`) rather than `ssr: false`.** With a static-only build, unknown paths would get the SPA fallback with a 200, or need a hand-built `404.html`. Keeping the server build lets the Worker render the 404 with a real status. It also leaves room for pages that can't be prerendered, such as event detail pages with their own link previews ([#27](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/27)), without changing the setup. The cost is a larger Worker upload (about 160 KB gzipped), which only runs for 404s and the API.

### Decisions recorded from planning

- **Content lives in the repo** as Markdown and data files, changed by pull request and read at build time ([#9](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/9)).
- **Events come from the club's Google Calendars, refreshed by a cron Worker into KV.** The board keeps editing in Google Calendar. Every 15 minutes, a scheduled Worker reads the Google Calendar API and stores the events in Workers KV, and `/api/events` serves them from there. Fetching from Google per request would be slow (about 0.3s per calendar), and a per-data-center cache would usually be cold on a low-traffic site. The cron keeps the API fast, works on preview URLs and keeps the last good copy through a Google outage.
- **The Calendar API, not the public ICS feeds.** The first version parsed the ICS feeds with ical.js, which took 8 to 20ms of CPU per refresh, over the free plan's 10ms limit per invocation. The Calendar API returns each occurrence already expanded, so the Worker only maps JSON, in about 1ms. Browsers can't call the ICS feeds themselves (Google sends no CORS headers), and calling the API from the browser would put the key in the page, so the Worker calls it with the key as a secret. Descriptions are reduced to plain text and links, and cancelled occurrences are kept with `cancelled: true` ([#16](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/16), [#17](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/17), [#18](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/18)).
- **Design system copied from dgtags**, light theme only ([#5](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/5), [#6](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/6)).
- **One font, Outfit,** for headings and body text. Headings stand apart by size and weight. The club's logos carry the display lettering, and a second font needs a clear job, such as monospace for code.
- **The contact form stays a Google Form** for the MVP ([#13](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/13)), and moves to our own form later ([#25](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/25)).
- **Tooling matches dgtags:** Bun, ESLint, Prettier, Vitest, Storybook and lefthook ([#2](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/2)).
- **Launch is staged:** first on `beta.mhdgc.org` for board review, then `www` moves over from the Google Site ([#23](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/23), [#24](https://github.com/mile-high-disc-golf-club/mhdgc.org/issues/24)).
